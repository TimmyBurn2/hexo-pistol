### 2.3 Can a reachable position provoke `NO_ONE_PLY_PARTNER`?

**No, and here is what I tried.**

1. **Analytic, from the rules.** A `WinWitness::OnePly { at, window }` asserts
   that placing one stone at `at` completes a run of six in `window` — so the
   witness's own premise is that the board already holds **five** of the
   mover's stones in that window. `crates/pistol-core/src/movegen.rs:104-109`
   returns `vec![Coord::ORIGIN]` only for an **empty** board; for any non-empty
   board the region is the union of radius-8 balls around the stones, and one
   ball alone is `1 + 3·8·9 = 217` cells. With five stones on the board the
   legal region is at least `217 − 5` cells, so `find(|cell| cell != at)`
   cannot fail. The guard is unreachable from any board that can carry the
   witness.
2. **Through the engine.** 2 040 broad searches plus the solver-armed seats
   (§1) on 40 fresh positions, three solver configs, `Provenance::SolverProof`
   reached — no panic on either side.
3. **Through the solver's own witness type.** `proof_first_move`'s OnePly arm
   is reached only from `solver_proof_outcome` (OR-rooted root proofs) and from
   `proof_line`. `git grep proof_first_move` finds exactly two call sites in the
   workspace, both in `search.rs`. The committed root-proof test
   (`wp18b_solver_path_tests.rs:105`) reaches a *Pair* witness, not a OnePly
   one.
4. **Coordinate-boundary route.** `region_cells` uses `saturating_sub` /
   `saturating_add` on the `q` bound, so a near-`i16` board clips the ball in
   one direction only; the remaining half-ball is still hundreds of cells. No
   construction gets the region down to one cell with five stones on it.

**Two things the change is NOT.** (a) It does not turn a graceful outcome into a
crash inside the engine: at `b60c3d3` a `None` from `proof_first_move` fell into
`solver_proof_outcome`'s own `panic!("… SOLVER_PROOF WITHOUT A MOVE …")`, so
both revisions panic on that board — only the message moves. (b) The second
panic arm (`Turn::pair(...).unwrap_or_else`) replaces a `.ok()` that could never
have produced `None` either: `Turn::pair` (`crates/pistol-core/src/turn.rs:124-132`)
errors on **exactly one** condition, `a == b`, which the `find(|cell| cell != at)`
predicate excludes. The replacement is strictly equivalent.

`proof_first_move` is `pub` and re-exported at `crates/pistol-search/src/lib.rs:63`,
so an out-of-tree caller that treated `None` as "no move" now gets a panic. D-676
rules this deliberately and the `# Errors`/`# Panics` doc says so.

### 2.4 Is the empty-board driver a legitimate reachable input?

**Partly, and the closure's sentence overstates it.**

What is reachable: the **state**. `GameState::new_game()` is the start of every
game, and `movegen.rs:107-109` makes its legal region exactly `{ORIGIN}`, so a
witness at the origin genuinely has no partner. That half is correct and I
confirmed it in the source rather than taking it.

What is **not** reachable: the **tree**. `one_ply_tree_at` fabricates an
`OrWinLeaf` whose witness claims a one-ply win **on an empty board** — a tree
the solver cannot emit, for the reason in §2.3 (a one-ply win needs five stones
in a window). The empty board also has `stones_owed == 1`, so a *pair* turn is
not the shape that position needs at all, and `one_ply_turn`'s own doc opens
with "a turn at `stones_owed == 2` is a PAIR". The test drives the guard through
a state in which the degeneration's stated premise is false.

**Why I do not call it contrived.** `proof_first_move` and `proof_line` are
`pub` and re-exported: an out-of-tree caller *can* hand them any `ProofTree`, so
the input is reachable **through the crate's public API**, which is a real
surface even though it is not reachable through a game. That is also the
principled line between E3 (pinned) and E4's two unpinned refusals
(`NO_COMPLETION_STONE` and `SOLVER_PROOF_WITHOUT_A_MOVE` sit behind *private*
functions, so no caller can reach them at all). The distinction is defensible;
it is just not the one the closure states, and the closure's E3 paragraph — "a
reachable input for a guard a real position cannot provoke" — does not mention
that the tree is fabricated.

D-553's call-site half **is** discharged: both tests drive the *call sites*
(`proof_first_move`, `proof_line`), not the private `one_ply_turn`, so a
call-removed mutant dies. See MINOR 5 for what the tests do not reach.

## Verdict

**FAIL.**

The code is right and the governing requirement is met: **byte identity holds**,
re-derived by an instrument that shares nothing with the closure's — 2 040 broad
searches plus 52 solver-armed searches and 223 census rows per side, with the
one licensed `id candidate_policy staged …` line as the only difference anywhere.
Every code-level attack in the dispatch came back clean: E1's dead-key premise is
true, the census merge is lossless, `one_ply_turn`'s new panic is unreachable
from any real board and its second arm strictly equivalent, `deny_unknown_fields`
refuses both keys by full path, and the eighteen config edits are exactly 36
key-line deletions.

It is FAIL for two reasons, both cheap to clear:

1. **The revision does not pass its own gate list.** `tools/file_justification_check.sh`
   exits 1 at `cb6e853`, and the only CI log in the tree is from `007f821`,
   before every commit in this package. Not group E's doing — but nothing about
   group E can be certified at a revision whose gates are red, and CLAUDE.md's
   Closure rule is explicit that `main` takes gate-passing merges only.
2. **E1 removed the keys from the code and left them in the documents.** Five
   configs, one public rustdoc, `census.rs`'s own design rationale, and the two
   governing specs the source code cites. Under D-424's test each of these

   `U3_tier_t.md` §10's template gets a refused document; a reader of

   calibration result. **This is the exact defect class E1's own commit message
   names**, left standing by the commit that names it, so it is a fix and not an
   overrule candidate.

Re-dispatch after the four rule-9 entries, the five comment deletions, the three
doc-comment corrections and the two governing-document amendments. Nothing in
the search needs to move, and the byte-identity evidence in §1 does not need to
be retaken.
