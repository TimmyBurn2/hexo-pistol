## Verification of the new gate (c) — the round's stake

**(c1)/(c2) split of labor — sound.** The division is: (c1) checks tree lines concretely with pistol-core alone (attacker moves legal and activating, defender-win on tree lines = named failure `DEFENDER-WIN-UNDER-SIGMA`, leaves core-checked); (c2) checks the whole-position adversarial value of P+σ. Coverage union, walked exhaustively:

- σ-illegal tree pair (σ on a free-stone cell) → skipped, adjudicated by (c2). I verified the parenthetical is a theorem, not an assumption: a blocking pair's cover stone lies in a plan's empty set ⊆ that node's Z_1 ⊆ root Z_1 ⊆ root Z_i, and σ_i ∉ Z_i — so σ can only ever occupy a pair's **free** cell. Nothing else can make a tree pair illegal in P+σ (region only grows, cells stay empty).
- Off-tree defender refutation (incl. σ-enabled blocking pairs, the round-2 "undischargeable" case) → (c2), which correctly does **not** use the non-edge completion rule (that rule is gate (b)'s, in P only).
- On-tree defender win → (c1) named failure. Broken activation / illegal attacker move → (c1) concrete checks (and I verified the design's no-kill argument: activated-window empties are child-Z_1 ⊆ root Z_1 by AT-1/T3-1 and zone monotonicity up the tree, so no σ can touch them — checked, not assumed, anyway).
- Double-counting: the legs overlap only redundantly (both must pass); no unsoundness.

**(c2) independence — no circularity that matters in v0, but the design argues the wrong reason (MINOR N-7).** The walkthrough requested, verified against the tree: `generate_turns` builds the region as the union of radius-`LEGAL_RADIUS` balls around **all** stones via `board.stones()` with no color filter (crates/pistol-core/src/movegen.rs:150-168), so on a P+σ board σ stones extend the region and σ-enabled pairs are generated; §2.4's children = `generate_turns(state)` filtered to covers, with step 1 (defender-wins-this-turn, core-based) checked first; the non-blocking⇒completion lemma and LAW-OVERLOAD are position-generic and only get *easier* under the region superset. So if Z_p is too small and a sampled σ enables a defender refutation, the solver on P+σ finds it and (c2) prints `NoWin` — the gate catches exactly the class it exists to catch. The load-bearing fact, which the design never states, is stronger than its stated vouching: **the solver's value path never consults zones at the registered `free_stone_radius = 8`** — certificate and oracle are independent artifacts, so a zone-construction defect cannot corrupt (c2)'s oracle at all. The stated "vouched by gates (a)+(b) on this class" is (i) ambiguous ("this class" — fixture class or P+σ class? only the former is true) and (ii) the weaker inductive argument. Note also the gate is intrinsically one-sided: it detects too-small zones (falsification) and cannot detect over-large ones (the sample shrinks with the zones) — inherent to Definition 3, covered by §3's disclaimer, not a defect.

**The σ-never-completes-six invariant — conclusion true, stated argument defective (MINOR N-2).** I verified the arithmetic independently: segment empties ⊆ Z_k (EP-1, order-3 cap: k ≥ 3 → Z_3); stone σ_i can lie in Z_k only if i < k (for i ≤ k, σ_k ∉ Z_k exactly and σ_i for i > k is excluded by Z_k ⊆ Z_i); so at most k − 1 of the k cells can carry σ — k=1: zero of one; k=2: one of two; k=3: two of three; k ≥ 4: |σ| ≤ 3 < k. With root active segments scanned at the root (a proof node), the invariant holds and exactly rules out P+σ being an already-decided defender win — the right role (sample well-formedness; without it (c2) would feed the solver a wrong-kind position, which §1 asserts loudly anyway). **But the design's sentence "σ_i avoids Z_i, so at least one of the k is excluded" is false at cell level for k ≥ 2** — no individual cell is excluded (for k=2, σ_1 may sit on either empty, in Z_2 \ Z_1); what is true is that the k cells cannot be *jointly* filled. Likewise "the k = 1 and k = 2 cases … excluded outright by Z_1/Z_2": k=2 is not excluded outright — only its completion is. Same ambiguity class round-2 MINOR G named; the true conclusion survives, the stated lemma does not.

**Canonical order / caps.** Caps (5000/2000, |σ|=1 uncapped) are pre-registered before the run with a registered no-shrink consequence — not a post-hoc shrink. But "canonical order" for σ **tuples** is not a defined term (MINOR N-3): `Coord`'s total (q, r) order exists (coord.rs:29-33, D-5/D-7) and `canonical_pair` normalizes pairs, but no order over 2- and 3-tuples is named, and the slot assignment "σ's i-th stone" of an unordered set is likewise unnamed. The slot ambiguity changes sample membership concretely: for {x, y} with x ∉ Z_2 and y ∈ Z_2 \ Z_1, the pair is in the class under the existential assignment (y as σ_1, x as σ_2) and out under ascending-canonical assignment.

**Cost pricing.** 60-min wall cap: registered number ✓, named failure ✓, registered consequence (fail, no shrink) ✓, ESTIMATED mark ✓, dry-run measurement registered in §10 ✓. But the "≤ ~5 000 solver calls per fixture" estimate is inconsistent with the registered caps' own arithmetic (MINOR N-4): a ≤ 10-stone clustered fixture has a ~250-400-cell region, so the pair and triple caps bind and the per-fixture count is ≥ 5000 + 2000 + ~250 singles ≈ **7 300**, and with ≥ 20 Win fixtures the leg is ≥ ~145 000 solves — the estimate is derivably wrong from the registration's own numbers (D-291-adjacent), and the dry run's stand-in (trivial win-in-one) measures the near-best-case σ-solve, not the depth-3-4 cost driver.

**Gate (b)'s defender-win check — closes MAJOR B.** "Every defender node applies EVERY legal turn through `GameState::place`" (`place` and `PlyOutcome::Win` exist with those semantics, state.rs:185-227) with defender-win a failure at every AND node — exactly the requested closure. The task's two-check question: the verifier does not assert child-set equality explicitly, but the spec supports both checks — a missing blocking pair is a legal non-edge, and a blocking pair leaves no surviving plan, so it *cannot* "concretely resolve as an attacker win"; the "must resolve" requirement forces failure (implicit, loud; rule 3 covers the no-plan disposition, though it is unnamed). Non-blocking non-edges resolve by completion — one turn, sound, since plans are hot windows (≤ 2 empties; confirmed by §7c's own "(hot windows)" gloss for k=1,2). Residual: the closure's cost (every legal turn ≈ 10⁵-10⁶ applications per AND node) is unpriced while MINOR F's discipline was applied to (c) only (MINOR N-8) — terminating by construction, so slow-not-hung.

**§10 dry run.** Externally-derived referents present (open five ⇒ Win, no live window ⇒ NoWin — both from the definitions); revision pinned to "the first commit where … actually solve positions" ✓. Residuals: MINORs N-5, N-6 below.

**Marking fixes.** M1 "ESTIMATED" ✓; §4 seesaw now "a to-be-measured number" ✓ (the new "no registered threshold registered" is a doubled-word slip); §7c σ counts ESTIMATED + dry-run measurement ✓. §9's "The seesaw number **is measured**" survives in present tense — defensible (the gates do measure it) but it is the class MINOR D named; cosmetic.

## NEW FINDINGS (against rev-3 material)

**MAJOR N-1 — the registered σ-class predicate admits occupied cells.** The operative sentence: "σ's i-th stone lies outside Z_i (all i), and all σ cells lie in **P's legal region**." The legal region includes occupied cells (`region_cells` measures balls around stones; movegen.rs:147-168), and `legal_placements` — the codebase's pinned term for "cells a stone may be placed on" — is region *minus* occupied (movegen.rs:134-139). The header's gloss "LEGAL pre-placements — cells of P's own legal region" glosses the correct term with the wrong set. This is not an edge case: **root stones are never zone cells** (zones contain only proof-move cells and cells that were unoccupied at contribution time — AT-1 adds move cells, EP-1/T3-1 add empties; P's own stones are neither), so every root stone's cell is outside Z_i and inside the region — the literal class includes *all of P's stones, on every fixture*. Failure modes: under `place`-construction (the §1 discipline, which binds the solver/reference/verifier but is not stated for the gate harness) an occupied σ is a named error → spurious gate failure; under direct board construction, σ on a root *defender* stone is a silent no-op → P+σ = P → the sample slot is consumed vacuously and the gate's confirmation power silently degenerates (EXIT-0 with a diluted gate — the wrong-answer direction for a gate whose job is confirmation). No false certificate of the RZ property is reachable, hence MAJOR not BLOCKING. Fix: "all σ cells lie in **the empty cells of** P's legal region" (`legal_placements(P)`), stated in the operative sentence, not only the gloss.

**MINOR N-2 — the σ-invariant's stated lemma is false at cell level** (detailed above): "at least one of the k is excluded" and "k = 1 and k = 2 … excluded outright" are wrong for k = 2 (σ_1 may sit on one empty; only the joint filling is excluded). The conclusion is independently verified true under m ≤ 3 and the order-3 cap, including the unspoken k ≥ 4 case (m ≤ 3 < k). Restate: at most k−1 of the k cells can carry σ stones.

**MINOR N-3 — "canonical order" for σ tuples is undefined, and the slot assignment is ambiguous.** `Coord`'s total order exists; the tuple-enumeration order ("the first 5 000") and the slot assignment ("the i-th stone" of an unordered set) are not named, and the existential-vs-ascending assignments differ on concrete pairs (reproducer above). Pin: cells ascending by (q, r); a σ held as an ascending tuple; "i-th stone" = i-th in that tuple; enumeration lexicographic over ascending tuples.

**MINOR N-4 — the cost estimate contradicts the registered caps.** "≤ ~5 000 solver calls per fixture" vs caps summing to ≥ 7 000 + singles whenever they bind (they will, on ~250-400-cell regions); ≥ ~145 000 solves over ≥ 20 Win fixtures under the 60-min cap. The cap and named failure govern, so the registration is not broken — the number is. Also: the dry run's stand-in measures best-case σ-solves, not the depth-3-4 drivers; note the extrapolation's weakness where §10 records it.

**MINOR N-5 — two dry-run criteria are unsatisfiable or vacuous at the pinned revision.** (i) "each gate assertion prints its own PASS/FAIL line" cannot fire at the revision the same paragraph pins as "the df-pn core in, **gates not yet**" — a criterion the registered dry run cannot show is not a criterion. (ii) "both print nonzero proof digests": §4 defines witness/proof recording for root `Win` only; whether a `NoWin` position prints a (disproof) digest at all is unspecified — if NoWin digests are zero-by-design, the criterion false-fails position 2. State what position 2's digest must be.

**MINOR N-6 — stand-in position 2 may not be of the same kind.** "Four scattered attacker stones with no live window of own ≥ 2" names no defender stones; registered-workload positions are mid-game with both colors, and §1's game-ongoing assertion (turn parity) may refuse a defender-less position. Position 1 includes defender stones; position 2 must say "plus N defender stones" (any placement not creating a live window concern).

**MINOR N-7 — (c2)'s independence note under-argues and is ambiguous.** "Vouched for by gates (a)+(b) on this class" — true only for the fixture class, and the note omits the fact that actually carries (c2): the v0 value path is zone-independent (`free_stone_radius = 8`, no pruning), so certificate and oracle cannot contaminate each other — and (c2)'s independence is therefore *conditional on the no-prune value*, a dependency the licensed future shrinking (M1 knob) would erode. Record the fact and the condition.

**MINOR N-8 — gate (b)'s full-width cost is unpriced.** "Every legal turn at every AND node" is ~10⁵-10⁶ `place`+win-check applications per AND node across the tree; MINOR F's pricing discipline was applied to (c) only. Terminating by construction (finite tree × finite turns), so a wall figure or an acknowledgement suffices — but the asymmetry is a discipline gap.

**MINOR N-9 — record fidelity: the rev-1 report misstates its own landing.** Its header says "Landed retroactively with **revision 2's fix round**"; `git log --follow` shows both report files first appear at `6dcd3ae` (revision 3) — the batch MINOR E demanded landed with rev 3, not rev 2. Content fidelity otherwise checks out: both reports' numbering and letters match the design's citations and the round summaries verbatim; no finding is softened.
