# Decisions

Append-only. One line per non-obvious design choice, in the form

    D-n: choice — reason — what flips it

Lines are never edited or deleted. A decision that changes is superseded by a
new line that says which one it replaces. Silent architecture drift is a breach
(CLAUDE.md rule 10); if the code and a line here disagree, one of them is wrong
and it is usually the code.

---

D-1: Crate cut = CLAUDE.md map verbatim, all 8 crates at workspace init, solver/arena/api as doc-only stubs in Stage 0 — churn-free dependency graph from day 1, stubs pin the seams at zero cost — flips if workspace overhead measurably hurts CI (it won't).

D-2: Engine trait is synchronous, no stop verb in v0 (new_game / set_position / go(Budget) -> SearchOutcome) — at <=0.5 s request/response a stop verb buys nothing and forces async plumbing through the one seam the future API wraps; stop/ponder arrive with Lazy SMP (Stage 4) as an additive trait extension + protocol verb — flips when the API spec requires cancellation.

D-3: Score = Eval(i32) | MateIn(u16) | MatedIn(u16), distance in TURNS; internally MATE = 30_000, MateIn(t) = 30_000 - t, eval clamped to +/-16_000; MateIn(1) means the side to move completes >=6 with a stone placed this turn (first or second stone, same turn count per rule 4); a turn cap scores static eval at the horizon, never 0/draw (rule 6) — flips if solver integration needs proof/disproof score kinds (additive enum variants).

D-4: Budget is the closed enum DepthTurns(u32) | Nodes(u64) | MovetimeMs(u64); absent budget = BudgetMissing; MovetimeMs under mode=instrument = InstrumentBudgetUnsupported — all three budgets exist in play mode, but determinism/strength claims only ever come from depth or nodes — flips never (the schema shape is the decision; values are operator config).

D-5: Line protocol v0 mirrors the Engine trait 1:1; stone token "q,r" signed decimal, pair token "q,r/q,r" canonical lexicographic by (q, then r); verbs pistol/newgame/position/go/quit; every malformed or illegal input yields one line "error <NamedError>: <why>" and the engine stays alive — this protocol IS the future API's semantic contract (Hard Rule 11) — flips if the API spec demands a different position encoding (the move-list form stays canonical regardless).

D-6: The move list is the canonical position encoding (unbounded board, no FEN analog); position set exists for fixtures and carries tomove + phase, with the phase-1 stone identified as the last listed stone of the mover; a set position already containing a >=6 run = IllegalPosition; a pair is legal iff SOME ordering of its two placements is legal under rule 5; movegen and perft count UNORDERED pairs — flips if a fixture format needs richer state (extend set, never relax validation).

D-7: Determinism design: no randomized-state maps on any choice path (fixed-seed hasher or sorted structures), stable sorts with lexicographic (q, then r) final tie-break, deterministic TT replacement (depth-preferred + generation counter, never wall time), integer-only eval, instrument mode = 1 thread enforced by config validation; CI gate = two-process CLI runs over sha-pinned fixtures x budgets {depth_turns 4, nodes 200000}, diffing bestmove + nodes + full pv, any diff = fail; a same-process double-run unit test additionally catches state bleed across newgame — Hard Rule 4 made executable — flips never.

D-8: Zobrist keys are 128-bit, computed as a pure function of (q, r, color, FIXED_SEED) via two independent SplitMix64 streams (caching optional, never value-affecting), XORed with side-to-move and intra-turn phase keys; the search TT indexes from low bits and stores the high 64 bits as verification (~24 B packed entries, 4-entry buckets, deterministic replacement); the solver TT (Stage 1+) stores the full 128 bits plus GHI history hooks; coordinates are i16 with loud overflow asserts — deliberate narrowing of the report's blanket 128-bit line: 64 verification bits are ample for heuristic search, full 128 is reserved for proof soundness where the report's argument actually applies — flips on any observed TT-verification collision in the determinism fixtures, or if solver and search ever share a TT (they won't).

D-9: A turn is represented internally as two sequential same-side plies with the intra-turn phase bit in state and zobrist key; all external accounting (depth, mate distance, perft) is in TURNS over unordered pairs; win check runs after each ply and a phase-0 win ends the turn — the alpha-beta cutoff between the two plies is the main pruning lever (report Section A) and rule 4 falls out structurally — flips never at this design point.

D-10: One EngineError enum in pistol-engine wrapping crate-local errors: Config{key, why}, IllegalMove{turn, why}, IllegalPosition{why}, Protocol{line, why}, BudgetMissing, InstrumentBudgetUnsupported, InternalInvariant{what}; validation = serde deny_unknown_fields on every struct PLUS a validate() pass for cross-field constraints, each failure a named Config error carrying the exact editable key — fail loud (Hard Rule 3) — flips never.

D-11: Eval v0 = handcrafted, integer-only, incremental: for each of the 3 axes every length-6 window through a cell; a window containing both colors is dead (0), else table[own_count] - table[opp_count] with all table values explicit in configs/eval_v0_weights.toml; one stone updates <=18 windows (3 axes x 6 offsets); the Eval trait contract (apply/undo per placed stone, side-relative integer value) is the SAME trait the Stage-2 codebook net implements — cheapest eval that produces sane depth-4-6 play; sophistication is Stage 2's job — flips if depth-6 play is pathological in obvious ways (adjust weights, not architecture).

D-12: Test strategy: an independently written brute-force reference generator in the test tree is THE movegen oracle (full radius-8 region by scan, ordered enumeration, unordered dedupe, rule-4 truncation; exact count equality at depths 1-3 turns over origin + hand-built midgame fixtures incl. a two-cloud union case); sha-pinned golden boards pin rules 2 and 4 (exact-six per axis, overline-7, five-is-not-win, first-stone-win truncation, second-stone win); tactical-v0 = ~20 sha-pinned mate/must-block positions with a pass threshold pre-registered in the fixture header before the first run — Hard Rule 7 — flips never.

---

D-13: One cargo workspace, members `crates/*`, edition 2024, `publish = false`, and `unsafe_code` denied workspace-wide — one toolchain surface for eight crates, and unsafe becomes a visible, per-crate opt-out rather than something that arrives unannounced in a hot loop — a measured hotspot that needs unsafe, which then documents the opt-out in its own line here.

D-14: No `[profile.release]` tuning in WP-01 — codegen settings are a perf-sensitive change and rule 5 wants a pre-registered hotspot, an expected gain bracket and an IQR-gated bench; there is no code to bench yet — the first benched work package, which sets them with numbers attached.

D-15: Config is TOML, parsed by serde with `deny_unknown_fields` on every struct, no serde field defaults and no `Default` implementation anywhere — rule 1; a mistyped key must be an error, and a value exists because an operator wrote it — an explicitly optional section, which would need its own line here first.

D-16: `schema_version` is a required top-level integer checked against `SCHEMA_VERSION` — configs outlive binaries, and version skew must fail at load rather than at the first divergent behaviour — a specified migration path, which would replace the equality check with a range.

D-17: Parsing and validation are separate calls and the parse-only entry point is named `parse_unvalidated` — cross-field rules cannot be expressed in serde, and the blunt name makes a caller that skips validation visible at the call site — a typestate wrapper that makes an unvalidated config unrepresentable instead.

D-18: `MIN_TT_BYTES` and `MAX_CANDIDATE_RADIUS` are rejection bounds, not values — code never completes a config, it only refuses an impossible one, so a config that omits the key is still an error — a bound that becomes a tunable itself, at which point it moves into the schema.

D-19: `search.tt_bytes` must be a power of two and at least 1 MiB — the table will index by masking, and a size that is not a power of two would have to be rounded; rounding a stated value silently is the failure mode this project forbids — a cluster-based table with non-power-of-two bucket counts.

D-20: `search.candidate_policy.radius` is validated against its own ceiling and is never compared with the rules' radius-8 legal region — they are different concepts, one a search knob and one a game rule, and conflating them is the mistake CLAUDE.md rule 2 names explicitly — nothing; a coupling would need its own line here and a very good reason.

D-21: `eval.weights_file` is validated for shape, not existence — config validation stays pure, offline and deterministic, and a missing or corrupt weights file is pistol-eval's loud error at load time — a deployment gate that must catch a missing artifact before a match starts.

D-22: `Budget` is a closed enum, an absent budget is `EngineError::BudgetMissing`, a zero budget is a named config error, and instrument mode refuses `MovetimeMs` with `EngineError::InstrumentBudgetUnsupported` — wall-clock is not reproducible and instrument mode is the source of every strength claim (rules 1, 4, 6) — a deterministic simulated clock.

D-23: `EngineError` implements `Display` and `Error` by hand rather than taking a `thiserror` dependency — the enum is small and closed, and its text is part of the operator contract, so it is written rather than generated — enough variant growth that hand-written text starts to drift.

D-24: Deserialization failures become `EngineError::Config { key, why }` with the key recovered by `serde_path_to_error` and spliced with the member named in the message — every rejection has to name a key an operator can go and edit, and serde alone reports the container — a schema layer with native path reporting.

D-25: Config validation ships as the `pistol-engine` example `validate_config`, not a pistol-cli subcommand — pistol-cli's surface mirrors the `Engine` trait one to one (rule 11), and config checking is a tools-side gate — a CLI that grows a general maintenance surface.

D-26: `tools/ci.sh`'s fresh-build gate builds a checkout of the git index, not a clone of `HEAD` — the gate exists to catch a build that depends on an untracked file, and the index is the tracked set in every state: it equals `HEAD` on a fresh checkout and equals the about-to-be-committed tree when work is staged, so a clone of `HEAD` would pass a working tree that is about to break CI — anything the build needs that lives outside the index, such as a submodule or a generated file, which would make a clone the honest thing to build.

D-27: `tools/artifact_check.sh` applies rule 7's 10 MB per-file ceiling to every tracked file, not only to fixtures — no tracked file has any business being that large, and one rule is easier to obey than two — a legitimately large tracked file, which would need its own line here.

D-28: pistol-core carries no code in WP-01, the radius-8 constant included — a rules constant ships with its pinning test in the rules work package, and an untested constant that other crates start reading is worse than no constant at all — the rules work package landing.

D-29: The no-code-side-default guarantee is enforced by a `compile_fail` doctest on `Config` plus a source scan over `config.rs`, `validate.rs` and `budget.rs` in `config_rejects_code_side_default_probe` — a rule that only lives in a review checklist rots quietly; this makes reintroducing a default a red test — a lint or macro that can express the same guarantee directly.

D-30: `tools/ci.sh` runs `cargo fmt --all --check` as a gate — added post-WP-01 by operator instruction; style drift is review noise, and reviewers are here to flag correctness and requirement gaps — flips never.

---

D-31: pistol-core raises its own closed `CoreError` (OccupiedCell, OutsideLegalRegion, FirstStoneNotAtOrigin, GameDecided, UnoccupiedCell, NothingToUndo) and pistol-engine wraps it per D-10 — core is std-only and cannot name `EngineError`, and a rules refusal has to be a value the rules layer can return; the engine maps it at the call site, where `state.turn()` supplies D-10's `IllegalMove.turn`, and `NothingToUndo` maps to `InternalInvariant` because no protocol line can provoke it — flips if the two crates ever merge, which they will not.

D-32: Board occupancy is a `BTreeMap<Coord, Color>` ordered by (q, r) — determinism by construction: no hasher, no per-process random state, and iteration a caller can observe is the same lexicographic order the protocol and the search tie-break already use (D-5, D-7) — flips when a bench names occupancy lookup as a measured hotspot, at which point the replacement (fixed-seed open addressing) goes behind the same `Board` API and is a benched change under rule 5, not a contract change.

D-33: Axes are named for the coordinate that stays CONSTANT along them, and the name says so: `Axis::ConstQ` direction (0,+1), `ConstR` (+1,0), `ConstS` (+1,-1) — naming an axis for the coordinate that varies has no consistent answer for the third axis, and the `Const` prefix keeps the invariant in the identifier that eval windows, threat lines and pattern indices will read a thousand times rather than in a doc comment beside it — flips never.

D-34: Coordinates are i16 and every coordinate arithmetic site is `checked_add`/`checked_mul`/`checked_neg` with an unconditional panic naming `COORD_OVERFLOW`, never a bare operator and never `debug_assert!` — i16 addresses some four thousand turns of legal-region growth, so leaving the range is a bug in pistol rather than operator input, and a `debug_assert` would leave the release build (which has no overflow checks, D-14) silently wrapping — flips if an analysis mode ever accepts operator-supplied unbounded coordinates, which would validate at that seam instead.

D-35: `Board` is storage plus the rule-5 region query and does NOT enforce reachability; `GameState::place` is the single entry point that enforces the whole placement rule — the golden fixtures and the union-of-balls test need synthetic positions no legal game reaches, and a container that refused them would be lying about what it is; the mitigation is that `GameState`'s fields are private, the board is handed out by shared reference only, and there is no `board_mut` (pinned by a compile_fail doctest) — flips never.

D-36: Win detection is `wins_at(&Board, Coord)` reading the colour from the board, with no colour argument, no whole-board scan, and a `WIN_CHECK_ON_EMPTY_CELL` panic on an empty cell — a colour argument admits a mismatch class with no legitimate caller, rule 4 only ever asks about the completing stone, and the panic is unreachable from the protocol path because every refusal a line could provoke is named and returned before the win check runs (so D-5's stay-alive still holds); `winning_run` reports the first axis in `Axis::ALL` order and a run start defined as the end reached against the axis direction, so neither is "whichever the scan reached first" — flips if position validation needs a scan, which arrives as an additive validation-only entry point.

D-37: The golden-board fixture is a line-oriented text format read by a strict test-tree loader (unknown directive, missing verdict, or a `last` stone that is not on the board = a panic naming the line) and pinned by a SHA-256 computed in the test tree from a std-only implementation that is itself pinned against the published FIPS 180-4 vectors — pistol-core takes no dependency, dev-dependencies included, and the pin has to fire in the test that reads the fixture so that `cargo test` alone catches drift rather than only a shell gate; win cases additionally assert the position WITHOUT the last stone has no completed run, so the fixture pins rule 4's completing stone and not merely a board — flips if the workspace ever gains a vetted hashing dependency.

D-38: `GameState` keeps a per-ply record (cell, mover, prior phase, prior turn) and undo restores it rather than recomputing the transition backwards — the search applies and takes back one ply per node (D-9), and a backwards transition would be a second implementation of the rules sitting next to the first; the outcome needs no record because a stone is only ever placed from an ongoing game — flips never.

D-39: The `"q,r"` stone token is parsed by `FromStr for Coord` in pistol-core, beside the `Display` that writes it, and rejects surrounding space, a space after the comma, a leading `+`, an empty field and a second comma — the token is a protocol contract (D-5), and a formatter shipped without its parser guarantees pistol-cli and every fixture loader write their own, which then drift on exactly the cases nobody tests — flips never.

D-40: An empty board refuses any cell but the origin with `FirstStoneNotAtOrigin`, a different name from `OutsideLegalRegion` — rule 5 imposes nothing on an empty board (there is no stone to measure from), the origin restriction is rule 3's without-loss-of-generality normalization, and a diagnostic that cites the wrong rule is the quiet kind of wrong; a game recorded with a different first stone is replayed by translating every stone by the same vector with `Coord::offset`, which is geometry and already lives in pistol-core — flips never.

D-41: `Board::apply`/`undo` is the per-stone seam that WP-04's incremental zobrist and D-11's incremental eval hook, and `GameState` composes it rather than owning a parallel copy of the same state — incremental state has to sit at the layer that actually mutates the stones, or a caller holding a `&mut Board` desynchronizes it — flips never while `Board::apply` is public.

D-42: `GameState::from_plies` replays a move list through `place` and is the only way to reach a position other than by playing to it — D-6 requires that a position handed in from outside must not already contain a completed line, and replaying makes that fall out of the one implementation of the rules instead of adding a whole-board decidedness scan that D-36 declines to ship — flips if a fixture format ever needs to state a position that no legal game reaches, which would need its own line here.

D-43: Rule 4's truncation cases live in a second sha-pinned fixture of MOVE LISTS (`golden_games_v1.txt`), not in the board fixture, and the turn-model and undo tests read their scripted games from it rather than from arrays in the test files — D-12 promises the pinned goldens cover the first-stone-win truncation and the second-stone win, and both are statements about WHEN a stone was played, which a board cannot express; a script sitting in a Rust array is exactly the thing that can drift without anyone noticing, which is what pinning is for — flips if a case ever needs a position no legal game reaches, which belongs in the board fixture instead.

D-44: Amends D-34's letter, not its intent: coordinate arithmetic that stays in i16 is `checked_*` with a named panic, and widening to i32 is the sanctioned alternative where the result is not a coordinate and provably cannot overflow (`Coord::s`, `Coord::distance` — the differences of two i16 always fit) — D-34 says "never a bare operator", which reads as absolute and is contradicted by those two functions and by the `i16::try_from` on a run length in `winning_run` (which panics with `COORD_OVERFLOW` rather than expecting) — flips never; the rule is that no i16-resident coordinate can wrap, and widening is not wrapping.

D-45: `GameState::undo` takes the stone off the board BEFORE popping the ply history, and panics with `HISTORY_DESYNC` if the colour the board hands back is not the one the history recorded — a mutation followed by a failure would leave the state half-taken-back, and the board and the history are two representations of the same game that are free to check each other; the seam D-41 designates for incremental zobrist and eval has no other way to notice a desync — flips never.

D-46: The `"q,r"` stone token is canonical — no leading zeros and no `-0`, so `display(parse(t)) == t` for every token the parser accepts and each cell has exactly one spelling — the token is a protocol contract (D-5, D-39), and a grammar that accepts `007,0` and echoes `7,0` lets two lines that differ mean the same move, which is a difference an arena log, a fixture diff, or a dedupe by string will eventually trip over — flips never.

D-47: `Coord::checked_step` judges a step by whether the DESTINATION is addressable, computed in i32, not by whether the intermediate `direction * steps` fits in i16 — the intermediate test refuses cells that exist (stepping `i16::MIN` along `ConstS`, whose `r` component is -1, needs an `r` delta of 32768 while landing somewhere ordinary), and `None` is read by the line scan as "no cell, so no stone", so a false `None` is a wrong answer rather than a conservative one — flips never.

D-48: `winning_run` carries the run's far end out of the scan that already stood on it, instead of recomputing it as a step count from the run length — supersedes the clause of D-44 describing an `i16::try_from` panic in `winning_run`: a line of this lattice holds 65536 cells, so a run can be longer than a step count can express, and `Board::apply` can build such a position by design (D-35); the old code turned a diagnostic call into a panic at 32769 stones while `wins_at` answered correctly — flips never.

D-49: A turn is the value `Turn::Single(Coord) | Turn::Pair(Coord, Coord)` with the pair canonical (smaller cell first, lexicographic by q then r), and `Single` carries all three one-stone cases — turn 1 (rule 3), a stone that completes a line as a turn's first stone (rule 4), and nothing else — while a stone that completes a line as a turn's SECOND stone stays an ordinary `Pair` — one turn needs exactly one representation or perft cannot dedupe by value and the TT cannot key on it, and rule 4's truncated turn genuinely is a turn of one stone rather than a pair with a flag; the play order is not part of the value because it is a legality question (D-6) that `make_turn` answers — flips never.

D-50: The turn-level API (`generate_turns`, `make_turn`, `unmake_turn`, `perft`) is defined only at a turn boundary and refuses a half-played position with `CoreError::TurnInProgress`; the ply-level `GameState::place` is what finishes such a turn — `unmake_turn` has to be the exact inverse of `make_turn`, and in a history that can contain a lone second stone the grouping of plies into turns is ambiguous, so the ambiguity is refused rather than guessed — flips when a mid-turn `set_position` has to move, which adds an explicit finish-the-turn entry point instead of relaxing this.

D-51: `make_turn` plays the canonical ordering of a pair and the reverse only if the canonical one is refused — including refused by rule 4, where the smaller cell completes a line and that ordering would play a turn of one stone instead of this pair — the same turn must always leave the same ply history behind or the zobrist path (D-8), the incremental eval (D-11) and any future repetition accounting depend on how a caller spelled it; every refusal takes its own stone back first, so a refused turn changes nothing — flips never.

D-52: Generation enumerates the union of the radius-8 balls around the stones and emits a pair whose two cells are both in that base region from the smaller cell only — unless the other cell wins, whose own enumeration emits nothing for it (rule 4) — with the cells outside the base region reached only through the ball the first stone opens; it does not enumerate ordered placements and dedupe — the emission is then exactly output-sized with no set on the hot path, and the three facts that make it correct (a pair with both cells outside the base region has no legal ordering, a winning cell is never half of a pair, a cell outside the base region is empty) are the ones the brute-force reference pins — flips when Stage 1's threat-first staged generator supersedes it, which is an additive candidate policy over this rule-complete set, never a replacement for it.

D-53: `CoreError` gains `IllegalTurn { turn, why: &'static str }` with the reason as a named public constant, plus `TurnInProgress { turn }` — the whole-turn refusals (a pair of one cell, an uncanonical pair, a stone count the turn does not owe, both cells winning) have no single cell to name, and D-10's `EngineError::IllegalMove { turn, why }` passes the reason through unchanged; a refusal that IS about one cell keeps its own variant and names it, so `make_turn` reports `OccupiedCell`/`OutsideLegalRegion` rather than wrapping them — flips never.

D-54: Perft counts TURNS with `perft(0) = 1` and a decided position generating nothing, so a won line is counted where it ends and never expanded; full depth 2 is checked only where it is reachable (from the initial position, and at a decided position) and the second level elsewhere by an exact divide over a deterministic sample of first turns against the same reference — measured branching factors: 42768 turns with one stone on the board, 54228 with five, and around 1.7 * 10^5 one turn deeper, so two full levels from a midgame position is 10^9 to 10^10 turns and no test run enumerates it; `tools/perft_check.sh` is the perft gate and runs the wide sample in release — flips if a materially cheaper reference ever makes a full second level affordable, which would be a widening of the sample, not a change of oracle.

D-55: The perft fixture states positions as MOVE LISTS and pins its counts by SHA-256, and every pinned count is cross-validated against the brute-force reference in the same test run — the same argument as D-43 (a position written as a heap of stones cannot say whose turn it is or which stones belong to the current one), and a count pinned only against the implementation that produced it pins nothing; the two-cloud union case is a bridged dumbbell rather than disjoint balls because every stone is placed within eight of an existing one, so the region a legal game builds is always connected — flips if a fixture ever needs a position no legal game reaches, which would need its own line.

D-56: The turn token `"q,r/q,r"` ships with its parser now rather than with the line protocol, and the parser refuses an uncanonical or doubled pair instead of repairing it — D-39's argument (a formatter without a parser grows its second implementation in whichever crate needs one first) and D-46's (one turn, one spelling, or two protocol lines that differ mean the same turn) apply unchanged to the pair token that D-5 already pinned — flips never.

D-57: The zobrist seed is `ZOBRIST_SEED = 0x706973746F6C0001` (`"pistol"` and a key-format version), and a key is two SplitMix64 streams over one 64-bit word `tag << 56 | payload`, the high stream seeded by the mix of the low one so that both descend from the single seed and no second magic constant is chosen; the tag separates the cell, side and phase families, and a cell's payload is its two `i16` coordinates in two's complement plus the colour — the word is injective and SplitMix64 is a bijection, so distinct inputs cannot share a key in the full 128 bits *or* in either half alone, which is the property the TT's 64-bit verification word (D-8) rests on and which a table of drawn random numbers would only have probabilistically — flips on a demonstrated weakness of SplitMix64 as a keyed hash, which would change the mixer and the version digit of the seed together and rename every position in every book, net and log keyed by the old one.

D-58: `Board` carries the stones' key incrementally (one XOR in `apply`, one in `undo` — the seam D-41 designates) and `GameState::key` composes it with `side_key(to_move) ^ phase_key(phase)` on read, rather than storing a full key that the transitions toggle — the side and the phase are already fields of the state machine that undo restores exactly (D-38), and a stored full key would be a second copy of them that can fall out of step in silence, while two XORs on read cannot; the turn number and the outcome are deliberately absent from the key, because in an ongoing game the stone count fixes the turn, the phase and the mover together, and a completed run is a property of the stones — flips if a bench names the composition as a measured hotspot, which is a rule-5 change behind an unchanged `key()`.

D-59: No key cache, though D-8 permits one — two SplitMix64 mixes are a few cycles and cheaper than any map probe that could memoize them, and rule 5 wants a pre-registered hotspot and an IQR-gated bench before a perf structure exists at all; `zobrist_key_is_pure_function_of_cell` asserts exactly what a cache would have had to preserve, so adding one stays a benched change rather than a redesign — flips on a bench that names `cell_key` as a hotspot.

D-60: The pinned key vectors in `tests/zobrist_key_tests.rs` were computed outside the implementation from D-57's construction, with the SplitMix64 they used checked against Vigna's published stream for state zero — a vector copied out of the code it checks pins nothing (D-55), and cross-process determinism (rule 4) is precisely the claim that a value computed elsewhere matches; the other half is the seeded-playout round trip, which checks the carried key against a from-scratch recompute over more than a thousand applied and taken-back stones and names a reproducible playout when it fails — flips never.

---

D-61: The `Eval` trait is exactly `apply(cell, colour)` / `undo(cell, colour)` / `value(side_to_move) -> i32`, object safe, total, and with the colour passed in rather than read off a board — the caller that moves the stone is the caller that updates the eval (D-41), a colour argument means an implementation never needs a board reference and can cross-check what it is told, an infallible signature is honest because every refusal a caller could provoke is already `GameState`'s (rule 3), and object safety lets the engine hold a config-selected backend without making every search type generic; the value depends only on the SET of stones applied, so neither apply order nor take-back order is part of the contract — flips if a backend needs whole-board context it cannot carry incrementally, which adds a sync-from-board entry point rather than changing these three.

D-62: v0 window bookkeeping is a `BTreeMap<Window, Counts>` keyed by `(axis, start)`, with an entry present exactly while the window holds a stone and pruned the moment it empties, and a carried `i64` sum from black's point of view — an unbounded board has infinitely many empty windows and none of them score, so the map is the position's whole eval state; pruning is what makes an unwound eval byte-identical to a fresh one, which `eval_apply_undo_roundtrip` asserts by value equality rather than by re-reading a score, and the `i64` means a position summing far past the band clamps rather than overflowing — flips when a bench names window lookup as a measured hotspot, which is a rule-5 change behind an unchanged trait.

D-63: A window holding `WIN_LEN` own stones scores `DECIDED_WINDOW_VALUE = EVAL_MAX` (16000) and is deliberately NOT a document entry — the config table stops at 5 because six own stones is a win, and a win's score is the search's mate band with a distance in turns (D-3), which no number in a weights file can express; eval stays total because the winning stone is on the board before the search asks anything, so it saturates the band instead of panicking — flips never; the value of a win is D-3's business and not this table's.

D-64: The eval weight table is its own document kind — `schema_version` + `backend` + `[table]` with keys `1`..`5` — with its own version and its own validator (the pistol-eval example `validate_weights`), and `tools/config_check.sh` tells the two kinds apart by the `_weights.toml` filename suffix — a weight table checked against the engine config schema is rejected for every key it does not have, which is the note WP-05 inherited from D-21's deferral; the `backend` key is what stops a Stage-2 codebook file from being read as a v0 table, and a misnamed weights file fails loudly as a config rather than passing silently — flips if a third document kind makes the suffix rule cramped, which would put an explicit kind key in every document and bump both schema versions together.

D-65: Weight values are rejected unless `table[1] >= 1`, the table strictly increases, and `table[5] <= EVAL_MAX` — bounds, not values (D-18): more own stones in a window is never worth less, and one window that alone saturates the clamp would make every deeper distinction invisible; the committed values (2/12/60/300/1500, marked OPERATOR-CONFIRM) are Stage-0 sanity numbers that Stage 4's SPSA/Texel replaces, and an edit to them is a strength claim under rule 6 — flips if a tuner demonstrates under SPRT that a non-monotone table plays better, which relaxes the bound with the evidence attached.

D-66: `validate_config --check-weights-file` performs the weights-file existence check D-21 defers, in the tools-side example rather than in `Config::validate` — D-21's flip clause is exactly this deployment gate; keeping it out of `validate()` keeps validation pure, offline and independent of the working directory, and the gate checks only that the file is there and readable, never its contents, which have a different schema and a different validator (D-64) — flips never; an engine that must refuse a missing artifact at load checks it at backend construction, not in config validation.

D-67: The eval window (length `WIN_LEN`, three axes, 18 per cell) is enumerated in pistol-eval, not pistol-core — a window length is a property of an eval backend and not a rule (Stage 2's codebook reads length-11 windows under the same trait), while the geometry it composes (`Axis::direction` through `Coord::checked_step`) still comes from core, so no rule is restated (rule 2); a window needing a cell outside the addressable lattice is not a window and is skipped, which is D-47's reading of `None` as "no such cell" — flips if Stage 1's threat generator needs the same enumeration, which moves this module into core rather than copying it.

D-68: The from-scratch eval reference lives in the pistol-eval test tree and is itself checked two ways — the cheap stone-driven enumeration against the incremental value at every ply of seeded playouts (over a thousand stones, down and back up), and that reference against a full bounding-box region scan on fixed positions — the cheap reference shares D-12's oracle role but also shares the implementation's central assumption (only a window holding a stone can score), and the region scan is the independent statement of it, too slow to run per ply and unnecessary there — flips never.

D-69: pistol-eval carries its own small copy of the `serde_path_to_error` key-splice that D-24 describes for the engine config — the dependency runs engine -> eval, so eval cannot borrow the engine's mapper, and a shared utility crate is not in the crate map (D-1); thirty duplicated lines is cheaper than either inverting a dependency or adding a ninth crate, and both copies are pinned by their own rejection tests — flips if a third crate needs the same mapper, at which point it earns a home rather than a third copy.

D-70: The eval's desync checks are opportunistic and say so: `apply` catches a window that would exceed `WIN_LEN` stones and `undo` catches a window that holds no stone of the colour being taken back, both panicking with `EVAL_DESYNC`, and neither mirrors the board's occupancy to catch every drift — a `Coord -> Color` map inside the eval would be a second copy of the board on the hot path, which is a cost rule 5 wants benched rather than assumed, and the real guarantee is the recompute-at-every-ply playout test (D-68) plus the fact that `GameState` refuses an occupied cell before an eval ever hears about it — flips if a search bug class turns up that pairs apply and undo wrongly in a way the playout test cannot see, which buys the occupancy mirror with a bench attached.

D-71: The search's internal unit is the ply and every unit it reports is the turn, and a root in the middle of a turn is refused with `SearchError::TurnInProgress` rather than searched — the depth, the budget, the mate distance and the principal variation are all turns, and a line that begins half way through one cannot be grouped into `Turn` values without inventing a one-stone turn the rules do not have (D-49); the ply-level `GameState::place` is what finishes such a turn, which is the same answer D-50 gives at the turn-level API — flips when a mid-turn `set_position` has to be searchable, which would report the opening half-turn as its own kind rather than relax this.

D-72: A mate distance counts EVERY turn from the root, both sides', so `MateIn(1)` is exactly D-3's "the side to move completes six this turn", a win for the side to move is always an ODD distance and a loss always an even one, and both plies of a turn carry the same distance because they carry the same turn number; the table re-bases a stored score by `state.turn() - root_turn` on the way in and out — the alternative, counting only the winner's own turns, makes `MatedIn` count the other side's turns and leaves the re-basing arithmetic half a turn wide, while rule 4 already scores sudden death in game turns — flips never.

D-73: The search's stop condition is its own closed enum `Stop { DepthTurns | Nodes | Deadline }` and the engine translates `Budget` into it at the composition root — which budgets a mode may use is operator-facing policy and stays in the engine (D-22), while stopping is the search's; the translation is not a copy, because `MovetimeMs` becomes the `Instant` it expires at, so the duration-to-deadline clock read happens in the engine and the search holds no path that computes a deadline of its own (CLAUDE.md rule 4) — flips if a search ever has to re-derive a deadline, which would take the clock as an injected parameter rather than reading it.

D-74: The stop condition is tested every `NODE_CHECK_INTERVAL` (1024) nodes at a node boundary, so a search given n nodes stops on node `n.next_multiple_of(1024)` on every machine and in every run, and the FIRST iteration is not interruptible — a search that returned no move would be the silent failure rule 3 forbids, so a budget below the cost of one full-width first iteration overshoots, and the overshoot is reported in `nodes` rather than hidden; the granularity is a pinned constant and not a tunable, because two runs at the same node budget have to be comparable — flips if a partially searched first iteration ever becomes usable, which needs a root that can answer with the best move found so far.

D-75: The transposition table is a power-of-two count of four-entry buckets of 24-byte entries, sized to the largest count that FITS inside `search.tt_bytes`, with `Table::bytes()` reporting what was taken — a 96-byte bucket never divides a power-of-two budget, so up to a quarter of it goes unused; that is a ceiling honoured rather than a stated value silently rounded (D-19), and for a power-of-two budget it yields exactly the entry count a padded 32-byte entry would have — flips if a non-masking index (a fixed-point multiply) benches at least as fast, which would spend the whole budget on entries.

D-76: Move ordering scores a candidate by applying the stone to the `Eval` backend, reading the value and taking it back — the evaluation IS the static pattern score, and a second opinion living in the search would be a second pattern implementation to keep in step; the cost is one apply/undo pair per candidate per node, which is this work package's registered hotspot and the first thing a Stage-1 bench should attack (an incremental per-cell score under the unchanged trait of D-61) — flips on that bench.

D-77: A candidate set is the policy's cells intersected with pistol-core's own legality answer, asked one cell at a time; the two radii are never compared, so a policy radius wider than the rules' region simply yields the region and this module never learns why, and an empty board is not a special case but the honest reading of a proximity policy — there is no stone to be near, so the policy restricts nothing and rule 3 decides alone — the shortcut this refuses ("the radius is at most eight, so every policy cell is legal") is precisely the comparison D-20 forbids — flips never.

D-78: No transposition cutoff is taken at a principal variation node (one whose window is wider than a single point), so a reported line always runs to the horizon or to a win — a cutoff returns a score without the line that proves it, and the line is what the protocol prints and what the cross-process determinism gate diffs (D-7) — flips if a bench shows the cutoffs are worth a shortened line, which would then have to be recovered from the table and would no longer be the line the score was proved on.

D-79: The search enumerates plies, so it reaches each pair twice, once per order, and relies on the transposition table to collapse the two at the node below; it does not restrict the second stone to cells above the first — a pair whose smaller cell is only reachable *after* the larger one is placed is legal (D-52), and a canonical-order restriction at ply level would silently drop it — flips with Stage 1's threat-first staged pair generation, which generates turns rather than plies and pays the dominance test once.

D-80: An iteration the budget interrupts is discarded as an answer and kept as work: the returned `SearchInfo` carries the last completed depth's line, score and depth, and the whole search's nodes, time and table occupancy — half a depth is not a depth, but the nodes were really spent, and per-side compute is a reporting requirement (CLAUDE.md rule 6) — flips never.

D-81: WP-06's measured Stage-0 floor, recorded as a finding rather than treated as a failure (CLAUDE.md rule 5): from the opening position on one core of the development machine, a release build reaches depth 6 turns in 9.5 s at candidate radius 1, depth 5 in 73 s at radius 2, and depth 4 in 27 s at radius 3 (the committed value), at 150k-230k nodes per second; inside the 0.5 s deployment budget that is depth 3 turns at radius 3 and depth 5 at radius 1 — full-width ply enumeration with no quiescence, no threat generation and no reductions is what the research report predicts, and the depth this buys is exactly the argument for Stage 1's threat-first generation, killers and history rather than for a wider radius — flips with the first Stage-1 change that moves it, which arrives with its own bench and SPRT.
